> **الدليل المرجعي العام (المستوى الأساسي):** إطار عمل هندسي مفتوح المصدر، يضع معايير موحدة وقوائم فحص دقيقة لتدقيق الأكواد، واختبار البرمجيات، وتقييم جاهزيتها للتشغيل في بيئات الإنتاج الحية.  
> **البنية المعمارية:** شجرة هرمية صارمة متعددة المستويات، تضمن سهولة التنقل والترابط بين المفاهيم العامة ونقاط الفحص البرمجية المباشرة دون فقدان السياق.  
> **الحيادية التقنية المطلقة:** الإطار مستقل تماماً عن أي لغة برمجة أو إطار عمل بعينه؛ إذ يرتكز على الأصول الهندسية المجردة القابلة للتطبيق على أي نظام برمجي، سواء كان تطبيقاً سحابياً، أو خادماً للميكروسيرفسز، أو أداة لسطر الأوامر.

---

> [!NOTE]
> ### 🤖 وُلد مع ثورة الذكاء الاصطناعي.. ليرتقي بـ "البرمجة التوليدية" (Vibe Coding) إلى المستوى المؤسسي
> تم **توليد وهندسة هذا الإطار بالكامل بواسطة الذكاء الاصطناعي**، وصيغت قواعده عبر حوار معماري صارم مع خبراء برمجيات بشريين.
> 
> في ظل الطفرة الكبرى لـ "البرمجة التوليدية والاعتماد على الذكاء الاصطناعي" (Vibe Coding)، أصبح المطورون يكتبون ويبنون ميزات كاملة في دقائق معدودة. غير أن هذه السرعة الفائقة عندما تفتقر إلى الانضباط الهندسي تنتهي ببرمجيات هشة ظاهرياً، تعاني من ثغرات أمنية متوارية، وابتلاع صامت للأخطاء، وتراكم مخيف للديون التقنية التي تفجر الأعطال عند أول ضغط تشغيلي حقيقي.
> 
> **جاء إطار CRF ليقدم الحل العملي:** إنه يضع ميزاناً حازماً يُخضع كود المطورين وكود الذكاء الاصطناعي لأعلى المعايير العالمية المعترف بها (مثل **ISO/IEC 25010** و **OWASP ASVS** ودليل **Google Engineering Practices**)؛ ليضمن أن ما يُكتب سريعاً يُبنى بمتانة ليعمل باستقرار ويدوم في الإنتاج.

## ⚡ خطوات البدء السريع: كيف تطبق الإطار في مشروعك وفريقك؟

1. **لكُتّاب الأكواد ومؤلفي التغييرات (فحص الـ 3 دقائق قبل الإرسال):**  
   قبل أن تطلب مراجعة الكود من زملائك، افتح [قائمة فحص المؤلف قبل الإرسال](./PRE_SUBMISSION_CHECKLIST.md)؛ ستساعدك في دقائق معدودة على تصفية 80% من الأخطاء والشوائب محلياً (مثل الكود الميت، والمفاتيح المسربة، والتحذيرات غير المعالجة).
2. **لمراجعي الكود وقادة الفرق (مراجعات موضوعية بنّاءة):**  
   ودّع الآراء الذوقية والجدل المشتت، واستخدم [دليل المراجعات القياسية](./CONVENTIONAL_REVIEWS.md) لتوحيد صياغة الملاحظات وربطها برمز الفحص المباشر (مثل: `issue (blocking) [CHK-RES-0501]`).
3. **لتدقيق الإصدارات وتقييم جاهزية الإطلاق (Release Gating):**  
   استخدم [بطاقة التدقيق التفاعلية وحاسبة التقييم](./AUDIT_SCORECARD.md) المكونة من 89 فحصاً لقياس نسبة المطابقة بدقة بالأدلة والبراهين واستخراج درجة المشروع من (A+ إلى F).
4. **لضبط معايير الجودة في طلبات الدمج (GitHub PRs):**  
   استعن بـ [قالب طلب الدمج الموحد](./.github/PULL_REQUEST_TEMPLATE.md) وضعه في مجلد `.github/` بمستودعك ليلزم كل مساهم بإثبات اختباراته قبل الدمج.
5. **لمساعدي ووكلاء الذكاء الاصطناعي (Cursor, Claude, Antigravity, Copilot):**  
   ادمج [مهارة فحص الكود (Agent Skill)](./integrations/ai_agents/SKILL.md) و [تعليمات النظام الوقائية](./integrations/ai_agents/SYSTEM_PROMPT.md) في بيئة التطوير، ليقوم الذكاء الاصطناعي نفسه بمراجعة كودك وكتابته وفق معايير الإطار تلقائياً.

## 💻 دليل تثبيت وتشغيل الأدوات البرمجية

يوفر الإطار أدوات تقنية مفتوحة ومجانية تتيح لك تشغيل الفحوصات آلياً في مشروعك أو ربطها بالذكاء الاصطناعي:

### 1. أداة سطر الأوامر (CRF CLI) ⌨️
لفحص مشروعك واكتشاف الأخطاء البرمجية من التيرمينال مباشرة دون الحاجة لأي تثبيت مسبق:

```bash
# تشغيل الفحص الآلي المباشر على مشروعك
node path/to/code-review-framework/tools/cli/index.js audit .

# قراءة تفاصيل أي نقطة فحص برمجية مع أمثلة الكود الصحيح والسيئ
node path/to/code-review-framework/tools/cli/index.js check CHK-RES-0501
```

---

### 2. خادم الذكاء الاصطناعي (Model Context Protocol - MCP) 🤖
لربط الإطار بمحررات الذكاء الاصطناعي مثل **Cursor** أو **Claude Desktop** أو **Antigravity** ليصبح الذكاء الاصطناعي خبيراً معمارياً فورياً في الـ 89 فحصاً:

أضف هذا المقطع في ملف إعدادات الـ MCP الخاص بمحررك (مثل `~/.cursor/mcp.json` أو إعدادات Claude):
```json
{
  "mcpServers": {
    "code-review-framework": {
      "command": "node",
      "args": ["path/to/code-review-framework/tools/mcp_server/index.js"]
    }
  }
}
```
* **الأدوات المتاحة للذكاء الاصطناعي بعد الإضافة:** `get_checkpoint` (جلب تفاصيل الفحص)، `search_checkpoints` (البحث الذكي في المعايير)، `audit_code_snippet` (تحليل ومراجعة أجزاء الكود)، `calculate_grade` (حساب درجات التقييم).

---

### 3. أداة الفحص الآلي في GitHub Actions (خطوط أنابيب CI/CD) 🛡️
لفحص طلبات الدمج (Pull Requests) تلقائياً ومنع دمج أي كود يحتوي على أخطاء حرجة، أنشئ ملفاً باسم `.github/workflows/crf-gate.yml` في مستودعك وضع فيه:

```yaml
name: 🛡️ Code Review Framework Gate
on: [push, pull_request]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: تشغيل فحص الجودة الآلي
        uses: wabdelgilil/code-review-framework/tools/github_action@main
        with:
          tier: '1'
          fail-on-violation: 'true'
```

## 📜 دستور وضوابط المراجعة الهندسية

تخضع جميع الفحوصات والتدقيقات في هذا الإطار للقواعد الدستورية الصارمة التالية:

1. **الموضوعية المطلقة والتجرد من المجاملات:**  
   يُحظر المديح الشكلي أو التغاضي عن الخلل المعماري. كل تقييم يجب أن يستند إلى وقائع ملموسة، وسجلات تشغيل حقيقية، ونتيجة قطعية لا لبس فيها (`PASS` أو `FAIL`).
2. **الاستناد إلى المراجع والمعايير القياسية المعترف بها:**  
   لا يُقبل أي فحص مبني على اجتهاد شخصي بحت أو ذائقة فردية؛ فكل بند مشتق من أصل معياري عالمي:
   * **ISO/IEC 25010:** معايير جودة وهندسة النظم والبرمجيات.
   * **ISO/IEC/IEEE 29119:** معايير دورة حياة واختبار البرمجيات.
   * **OWASP ASVS:** الدليل القياسي للتحقق من أمان وحماية التطبيقات.
   * **The Twelve-Factor App:** منهجية بناء التطبيقات السحابية الحديثة.
   * **Google & Microsoft Engineering Practices:** أدلة كبرى الشركات في مراجعة الأكواد واستقرار النظم.
3. **استقلالية الاختبارات ومنع التزكية الذاتية (Anti-Gaming):**  
   تُبنى الاختبارات وقوائم الفحص انطلاقاً من المواصفات والمتطلبات الخارجية للبرمجية، ويُمنع اشتقاق الاختبار من الكود المكتوب تفادياً للتزكية الذاتية الدائرية. كما يُعد باطلاً ومرفوضاً أي اختبار شكلي لا يفشل عند إحداث عيب متعمد في الكود (Mutation Testing).
4. **الالتزام بالقياس الرقمي والحدود القاطعة:**  
   تُلغى العبارات الفضفاضة مثل ("كود سريع" أو "تصميم أنيق")؛ ويستعاض عنها بمقاييس كمية ملزمة: زمن استجابة مقاس بالمللي ثانية، ونسبة تغطية للفروع المنطقية، ومعدل تعقيد حسابي محدد $O(N)$.
5. **حتمية السلوك وقابلية إعادة الإنتاج (Determinism):**  
   المدخلات المتماثلة يجب أن تنتج مخرجات متماثلة دوماً على أي منصة أو بيئة، ويُرفض رفضاً قاطعاً عذر "الكود يعمل بنجاح على جهازي الشخصي".
6. **الفشل السريع وحظر الابتلاع الصامت للأخطاء (Fail-Fast):**  
   البرمجية الهشة هي التي تكتم أخطاءها خلسة أو تُخرج نتائج تقريبية مشوهة دون تنبيه؛ أما البرمجية المتينة فتتبنى مبدأ "الفشل الصريح والسريع" وتوقف التنفيذ فور مواجهة حالة غير صالحة مع إصدار تشخيص واضح لسبب العطل.
